## 目的とユーザー要件

- mimとpretrained_segに、エンコーダの各層の中間特徴マップを保存する新しい実験とinferenceメソッドを追加する。
- 下流タスクは、複数の代表点の特徴ベクトルを抽出してクラスタリングすること。
- 下流タスクはmdmethodsとは別の新しいディレクトリで実施する。座標変換と特徴読み取りを再利用しやすくする。
- mimは `experiments/mim/experiments/maskratio0_6.py` を参照し、pretrained_segはexperiment指定なしの設定を参照する。
- 元の実験コードは変更せず、継承などで新しい実験を追加する。
- CLIの共通引数は既存実験から引き継ぐ。
- 症例全体をplanのパッチサイズ、各軸overlap 0.5で分割し、全パッチの特徴を保存する、というのが当初の案。
- 出力先は従来どおりlib・実験名・日時を付け、その下に症例ディレクトリを作る。
- 元画像と、存在すればラベルへのsymlinkを症例ディレクトリに置く。

```text
{output-dir}/{lib}/{experiment-name}/{日時}/{case-id}/
    features.zarr/
    image.nii.gz -> 元画像
    label.nii.gz -> 元ラベル（存在する場合）
```

```text
features.zarr/
    patch-meta/
        start-zyx       # (N_patch, 3)
        end_zyx         # (N_patch, 3)
        metas/
            ...
    features/
        stage1          # (N_patch, C, Z, Y, X) を想定
        stage2
        ...
```

`start-zyx` と `end_zyx` はユーザーが示した名前。命名を統一するなら実装前に決める。

## 提案段階の設計（未確定）

以下は相談時の提案であり、全項目の採用は未承認。

### 抽出処理

- MIMはmaskratio0_6で学習したcheckpointを使い、特徴抽出時はマスクをかけずエンコーダへ直接入力する。
- stem出力から最深層までを浅い順にstage1、stage2、…として保存する。stage名と元のmodule名の対応も記録する。
- decoderは特徴抽出に使用しない。
- 既存checkpointのbuilderと重みを厳密に読み込み、checkpoint互換性を保つ。
- パッチ末端を画像末端へ合わせて全域を覆う。この場合、末端付近の実際の重なりは0.5より大きくなり得る。
- パッチごとに順次保存し、全パッチの特徴をRAM/GPUへ蓄積しない。
- 保存dtypeはfloat32/float16から選択可能にする案。既定値は容量と精度を評価して再決定する。
- 既存の症例出力を上書きしない。途中失敗した出力を完了済みと誤認しない仕組みも検討する。

### 座標とメタ情報

前処理後の座標だけでは、別プロジェクトで元画像上の代表点から特徴を取得しづらい。元画像・前処理後・パッチ・各stageのグリッド間を変換できる情報を保存する。

既存の `planned_transformd` にはforeground crop、spacing変更、強度処理、paddingがある。planだけでは症例ごとのcrop位置などを復元できないため、症例固有の変換情報も必要。

症例共通のZarr attributes候補:

- 元画像と前処理後画像のshape、voxel-to-world affine。
- 配列軸順と物理座標系（例: RAS、単位mm）を明示。
- crop位置、padding量、有効領域。
- 使用したplanの内容、checkpointの識別情報、前処理設定。
- 保存形式と前処理のバージョン。

パッチ単位の候補:

- 前処理後画像内の開始・終了座標。終了は排他的。
- パッチ内voxelから物理座標へのaffine。
- paddingを除いたパッチ内の有効領域の開始・終了座標。

stage単位の候補:

- 元のmodule名、チャネル数、空間shape。
- 特徴グリッドからパッチの入力グリッドへの変換。strideだけでなく原点のoffsetも確認する。

元画像側のパッチ範囲はspacing変更により整数座標の直方体として表せない場合があるため、開始・終了の整数座標を重複保存するよりaffineで表現する案。

重要: 現行コードのテンソルには `(B,C,H,W,D)` という記載もあり、NIfTI読み込み後の軸順をZYXと仮定してはいけない。実装時はplan、読み込み、affine、実テンソルの対応を確認し、必要なら明示的に軸を並べ替える。

### 独立した読み取りユーティリティ

`experiments` に依存しない小さなPython APIとCLIを追加する案。

- 元画像voxel座標または物理座標と、症例のZarrを受け取る。
- 前処理後座標、その点を含むパッチ一覧、各stage内の連続座標を返す。
- 三線形補間で特徴ベクトルを取得する。
- overlap領域は「中心に最も近いパッチを選ぶ」または「複数パッチを平均」で集約する。
- 初期案では中心に最も近いパッチを既定とする。パッチ端の影響を避ける目的。
- 画像外・paddingのみの点は検出し、黙って端へ丸めない。
- 座標だけ変換する場合はネットワーク、CUDA、学習環境を不要にする。

## 容量見積もりと中止理由

前処理後も1症例 `(512,512,1024)`、8,000症例と仮定した。元画像のshapeである場合はcropとspacing変更で結果が変わる。

参照した `plans/ttsgPlans.json` の3d_fullresと現行実装では:

- Planが返すパッチサイズは `(128,112,112)`。
- overlap 0.5で末端を含めると `7 × 9 × 18 = 1,134` パッチ/症例。
- stemを含めたチャネル数は `[32,64,128,256,320,320]`。
- 対応する空間縮小率は各軸 `[1,1,2,4,8,16]`。
- 最初のpoolが1なので、stemに続くstageも等解像度になることに注意。

非圧縮の概算（10進単位）:

| dtype | 1症例・1モデル | 8,000症例・1モデル | MIMとpretrained_segの両方 |
|---|---:|---:|---:|
| float32 | 約850 GB | 約6.8 PB | 約13.6 PB |
| float16 | 約425 GB | 約3.4 PB | 約6.8 PB |

float32の1症例あたりの内訳は、浅い順に約233 GB、466 GB、117 GB、29 GB、4.6 GB、0.57 GB。浅い2層が大部分を占める。

計算式:

```text
N_patch = product(ceil((image_size - patch_size) / stride) + 1)
stride = patch_size * 0.5
bytes = N_patch * sum(C_stage * product(stage_spatial_shape)) * bytes_per_element
```

この式は今回の画像が全軸でパッチ以上の場合。小さい画像ではpaddingを含めて計算する。

Zarrの圧縮率は未計測で、削減率の保証はない。メタ情報とsymlinkの容量は特徴本体に比べ小さい。実際の使用checkpointで構成が異なれば再計算する。

## 再開時に検討する容量削減案

今回の下流用途では、代表点の特徴ベクトルだけを推論時に抽出・保存する方式が候補。全マップ保存から仕様変更になるため、採用前に確認する。

- 全6出力を連結すると1点1,120次元。
- 1症例1,000点、パッチ間集約後に1点1ベクトルなら、float32で4.48 MB/症例、8,000症例で35.8 GB/モデル。
- float16ならその半分。両モデルを保存する場合は2倍。
- 後から新しい代表点を追加する場合は再推論が必要。

他の候補は、保存stageの限定、空間解像度の削減、overlap部分の集約など。いずれも元の全パッチ・全層保存とは情報が変わるため、下流用途に合うか評価する。
